## Design and implementation

In this example, you have to provide a pre-trained NN model with weights, regression data, and model parameters. The DEEPCRAFT&trade; Model Converter tool can generate such data in the standard Keras H5, TFLite, or PyTorch format. By default, these files are located in the *./deepcraft* folder for each core project (*proj_cm55* and *proj_cm33_ns*). The code examples also provide a DEEPCRAFT&trade; Model Converter project file *project.byom* for each core project, which points to the pre-trained NN model available in the *pretrained_models* folder.

If you change the output file location in DEEPCRAFT&trade; Model Converter, reflect the change to the `NN_MODEL_FOLDER` parameter in the *Makefile* file as well. The model data is stored in *.c*/*.h* files (used for filesystem applications). The application uses the files and variables from the following table, where 'KEY' refers to the *Output File Name* defined by DEEPCRAFT&trade; Model Converter:

**Table 1. DEEPCRAFT&trade; output files**

Folder name                          | File name | Description
:--------                            | :-------- | :------------ 
*deepcraft/mtb_ml_models*            | *KEY_&lt;engine&gt;_model_&lt;type&gt;.h/c* | Contains the model binary (`KEY_model_bin[]`), its length (`KEY_MODEL_BIN_LEN`), and the tensor arena size (`KEY_ARENA_SIZE`)
*deepcraft/mtb_ml_regression_data*   | *KEY_tflm_x_data_&lt;type&gt;.h/c* <br> *KEY_tflm_y_data_&lt;type&gt;.h/c* | Contains the input (x) and output (y) regression data used for local validation

<br>

The application consumes the model binary through the `MTB_ML_INCLUDE_MODEL_FILE`/`MTB_ML_MODEL_BIN_DATA` macros and the regression data through the `MTB_ML_MODEL_X_DATA_BIN`/`MTB_ML_MODEL_Y_DATA_BIN` macros, resolved for the selected `NN_TYPE` and `NN_INFERENCE_ENGINE`.

DEEPCRAFT&trade; Model Converter supports quantizing data while deploying an int8x8 or int16x8 model. The ML middleware initializes the model with `mtb_ml_model_init()`, feeds each input tensor with `mtb_ml_model_inputs()`, runs the inference with `mtb_ml_model_invoke()`, and retrieves the concatenated result with `mtb_ml_model_load_output()`.

In *Makefile*, set the `NN_MODEL_NAME` parameter based on the *Output File Name* chosen in the DEEPCRAFT&trade; Model Converter tool.

After updating *Makefile*, all model files are built into the application automatically, allowing the NN inference engine to be initialized and fed with regression data.

The placement of the model weights is controlled by the `CY_ML_MODEL_MEM` define in the *Makefile*, which points to the memory section where the weights are stored. By default, the CM33 application uses `.cy_sram_code`, which gives the best speed for CM33 + NNLite, and the CM55 application uses `.cy_socmem_data`, which gives the best performance for CM55 + Ethos-U55. The weights can also be placed in flash by changing the memory section this symbol points to; flash is larger but slower.

> **Note:** Some devices among the supported kits may not have enough memory to run some of the configurations listed earlier, particularly when using local regression data. If this occurs, select a different kit with a larger memory device or reallocate memory in the device configurator.
   
<br>

When profiling is enabled, the report includes the average CPU cycles, peak CPU cycles, and peak CPU frame. If an NPU is used, the average NPU cycles, peak NPU cycles, and peak NPU frame are included.

During local validation, the application automatically loads the regression data generated by the DEEPCRAFT&trade; Model Converter tool, which consists of inputs (x) and outputs (y). After processing the input data, the inference engine generates the result. For each output tensor, the firmware compares the class with the highest confidence against the reference (contributing to the accuracy calculation) and computes the Mean Absolute Error (MAE). The model output is converted to floating point with `mtb_ml_utils_model_dequantize_tensor()`, and the reference data is dequantized using the output tensor's `scale`/`zero_point`, so the two can be compared in the floating point domain.

### Enabling DEEPCRAFT&trade; model profiling

Profiling is configured through the `PROFILE_CONFIGURATION` macro in each project's *main.c*, which is passed to `mtb_ml_model_profile_config()` during `ml_validation_init()`. The available options are:

- `MTB_ML_PROFILE_DISABLE` – disable profiling
- `MTB_ML_PROFILE_ENABLE_MODEL` – profile the model (default)
- `MTB_ML_LOG_ENABLE_MODEL_LOG` – enable the model profiling log

The middleware measures the inference time using a timestamp counter (`mtb_ml_model_profile_get_tsc()`), which the code example implements in *elapsed_timer.c*. After the regression loop, `mtb_ml_model_profile_log()` prints the collected profiling results.

### Streaming validation

When `ML_VALIDATION_SOURCE=stream` is set in *common.mk*, the regression data is not compiled into the firmware. Instead, the device runs `ml_validation_stream_task()`, which:

1. Initializes the UART streaming interface with `mtb_ml_stream_init()`
2. Receives each input sample from the host with `mtb_ml_stream_input_data()`
3. Feeds the input tensors, invokes the model, and loads the output
4. Streams the output back to the host with `mtb_ml_stream_output_data()`
5. Sends the profiling log and signals completion with `mtb_ml_inform_host_done()`

The host tool — the DEEPCRAFT&trade; Model Converter "Validate on Target" feature — provides the input data and computes the accuracy from the returned outputs. In this mode the UART baud rate is raised to 1 Mbps.

### Performance improvements for inferencing

**Changing the Ethos-U55 cache management type**

When using the Ethos-U55, you can choose three different cache management types:

- **`MTB_ML_ETHOSU_CACHE_MGMT_ALL_LAYERS`:** Clears and invalidates the cache by address for each layer using cache-API calls within the driver (default option)
- **`MTB_ML_ETHOSU_CACHE_MGMT_CONDITIONAL`:** Clears or invalidates the entire cache based on an internal state. It can reduce the total number of CPU cycles, but it can cause undesired behavior in the application
- **`MTB_ML_ETHOSU_CACHE_MGMT_OUTER_LAYERS`:** Clears the input layer before executing the inference and invalidates the output layer after executing the inference. Use only if all operators are supported by Ethos-U55. It always provides the best performance

You can set `MTB_ML_ETHOSU_CACHE_MGMT_TYPE` in the **DEFINES** list in *proj_cm55/Makefile* or call `mtb_ml_set_cache_mgmt_type()` function to change the cache management type to one of the above options. By default, the Makefile is configured to use `MTB_ML_ETHOSU_CACHE_MGMT_ALL_LAYERS`.


### Multi input multi output support

The DEEPCRAFT&trade; Model Converter supports multi-input, multi-output (MIMO) models. The ML middleware exposes the model's input and output tensor descriptors (`model_obj->inputs[]` / `model_obj->outputs[]`, with their `count`, `elements`, and `concat_offset_bytes`). The validation task feeds every input tensor before invoking the model:

**Table 2. Function descriptions**

Function name              | Description
:--------                  | :-------- 
*mtb_ml_model_inputs*      | Loads the data for one input tensor (selected by index) into the model. For MIMO models this is called once per input tensor, using each tensor's `concat_offset_bytes` to locate its slice in the concatenated input buffer
*mtb_ml_model_invoke*      | Runs the inference once all input tensors have been loaded
*mtb_ml_model_load_output* | Concatenates all output tensors into a single result buffer for further processing (accuracy/MAE or streaming back to the host)
*mtb_ml_model_get_output_tensor* | Retrieves the buffer and element count of a single output tensor (selected by index, 0 to `output_count`-1), instead of the concatenated buffer. For single-output models, `mtb_ml_model_get_output()` is a convenience wrapper that returns the first output tensor
